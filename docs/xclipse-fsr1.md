# Experimental FSR 1 upscaling blits on Xclipse

This fork includes AMD FidelityFX Super Resolution 1 EASU edge-adaptive upscaling
followed by RCAS sharpening, using AMD's original FP32 shader functions.
The existing Anti-Lag changes remain included. FSR 1 and Anti-Lag are independent:
Anti-Lag still requires the application to enable and call its Vulkan extension.

## Enable

The filter is **off by default**. Set the environment before starting the application:

```sh
RADV_XCLIPSE_FSR1=1
```

Or set the Android property, then fully restart the game/emulator:

```sh
adb shell setprop debug.radv_xclipse_fsr1 1
adb shell setprop debug.radv_xclipse_log 1
```

Mode `1` filters eligible blits into native Android presentation images or
driver-owned WSI images. An explicit environment value overrides the property,
including `RADV_XCLIPSE_FSR1=0` to disable it.

Mode `2` is a diagnostic option that also permits eligible offscreen blits:

```sh
adb shell setprop debug.radv_xclipse_fsr1 2
```

Mode `2` may also filter non-presentation images and is unsuitable as a global
default. Return the setting to `0` after testing, and restart the application.
No change to graphics settings or device identity is required by this code.

## When it runs

The application must submit a full-image, linear-filtered `vkCmdBlitImage` or
`vkCmdBlitImage2` from a smaller SDR image into a larger image. Both dimensions
must grow, by at most 2x per axis. For example: a 1280x720 source blitted to a
1920x1080 presentation image. The driver does not lower render resolution or
replace swapchains on its own. The application/emulator must provide the
lower-resolution source and perform that blit.

If the game renders directly at display resolution, uses a shader-based upscale,
or relies on compositor scaling, the filter does not run. In particular, reducing
the game's resolution alone does not prove the FSR path is being used.

Accepted inputs are single-sample, single-mip, single-layer 2D RGBA8/BGRA8 images,
with matching source/destination Vulkan formats (UNORM or sRGB). Internal views
operate on display-encoded SDR values, bypassing automatic sRGB conversion.
HDR, depth/stencil, partial regions, flips, downscales, nearest-neighbor filtering,
multiple regions, sparse/protected images, secondary command buffers, and
simultaneously reusable command buffers keep the original blit path.

FSR normally belongs after tone mapping/antialiasing and before UI/noise effects.
A driver cannot identify those stages generically. This experiment filters the
whole submitted blit, including UI already drawn into the source image.

## Confirm it is active

With diagnostic logging enabled, the first eight recorded FSR blits per process
report their input/output sizes:

```text
[FSR1] EASU+RCAS 1280x720 -> 1920x1080 mode=1
```

```sh
adb logcat -s RADV_FSR1
```

The marker means that FSR work was recorded. It is not proof of successful GPU
execution or of an FPS/latency improvement. If no marker appears after enabling
logging and restarting the process, the filter may not have found a matching
blit; do not assume it is active.

## Implementation and cost

EASU runs in 8x8 compute workgroups and writes packed RGBA8 scratch. A memory
barrier makes its writes visible to the RCAS fragment pass, which renders the
destination image. RCAS uses a fixed 1.0-stop sharpening setting (half of maximum
strength), with clamped border reads and passthrough alpha. The intermediate
requires four bytes per output pixel, about 7.9 MiB at 1920x1080, per recorded
blit. The command buffer owns the memory until reset/destruction; allocations
are capped at 64 MiB per blit. Pipelines are cached per device/target format.

Both passes add GPU work. Compare against native rendering and ordinary
low-resolution scaling. At the same lower input resolution, FSR is intended to
improve upscale quality, and may cost more GPU time than the original blit.
FPS gains require savings from lower-resolution rendering to exceed that cost.

## Build and checks

Use the existing `build.sh`, `build.cmd` or `build-wayland.sh`; both FSR shaders
are generated by the existing glslang build dependency. No FSR SDK installation
is needed. AMD headers and notices are included in the source and binary notice.

```sh
python3 src/amd/vulkan/tests/anti_lag_regression.py
python3 src/amd/vulkan/tests/fsr1_regression.py
```

The FSR host harness checks eligibility/exclusions, strict option parsing,
constant setup against AMD's reference, and compilation/validation of the real
EASU and RCAS GLSL/SPIR-V. It needs `cc`, `c++`, and `glslangValidator` in PATH
(or `CC`, `CXX`, `GLSLANG_VALIDATOR` overrides).

Local verification also configured Mesa with Meson and compiled the changed
`radv_meta_blit.c`, `radv_image.c`, and `radv_physical_device.c` translation units
for the host, using this repository's Android stub include directory for its
logging declarations. An additional syntax check enabled Android native-buffer
declarations in the blit file. These checks do not constitute an Android build.
The host address-sanitizer run disabled leak scanning because the execution
environment does not permit its `/proc` scan; address and undefined-behavior
checks remained enabled.

This change still needs an Android driver build and testing on a physical
Xclipse. Compare FSR off/on with the same scene and input/output resolution,
inspect borders, alpha, color and UI, and record frame times/temperature. To
separate effects, compare neither feature, Anti-Lag only, FSR only, and both.
